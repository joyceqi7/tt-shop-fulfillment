# Game Code Hub 后台用户手册

> 适用版本：admin v0.1（看板 / 订单 / 库存 / TT 商品 / SKU / 供应商 / 采购单 / 财务 / 用户 / 审计）
> 访问入口：`https://tts-admin.sailson.com`
> 更新日期：2026-06-18
>
> 本文按**真实业务流**编排：TT 商品同步 → SKU 匹配 → 供应商建档 → 下采购单 → 卡密入库 → 订单履约 → 异常处理（退货 / 重发 / 作废）→ 财务对账 → 审计追溯。
> 所有金额**单位均为美分**（cents）。系统里输入 `100` 表示 $1.00。

---

## 0. 全局约定

### 0.1 登录与会话
- 用户名 / 密码由管理员在「用户管理」创建；首次部署时会用 `.env.production` 里的 `ADMIN_USERNAME` + `ADMIN_PASSWORD_HASH` 自动创建第一个管理员
- 连续输错 5 次 → IP+用户名锁定 15 分钟
- 会话默认 8 小时过期，过期后任何操作自动跳回登录页
- 登出按钮在右上角

### 0.2 角色与菜单速查

不同角色登录后看到的菜单不一样，后端 API 也会做同样的权限校验。

| 角色 | 常用人群 | 能做什么 | 不能做什么 |
|---|---|---|---|
| `admin` | 负责人 / 系统管理员 | 全部功能、用户管理、审计日志、API 凭证、自动采购开关 | 无 |
| `ops` | 运营 | 看板、订单、库存、TT 商品、SKU 映射、供应商采购 | 财务、用户管理、API 凭证 |
| `purchase` | 采购 | 库存、TT 商品、SKU、供货商、采购单、API 批量采购 | 用户管理、审计、API 凭证 |
| `finance` | 财务 | 财务、采购单查看/付款、供货商只读 | 订单重发、库存导入、SKU 修改 |
| `support` | 客服 | 看板、订单查询/重发、库存/SKU/TT 商品只读、供应商采购只读 | 采购、财务、用户管理 |

> 高风险项：API 供货商凭证、自动采购开关、用户管理、审计日志只给 `admin`。

### 0.3 数据状态约定（很重要）

**订单状态**（来自 TT 平台原值）
- `UNPAID`、`AWAITING_SHIPMENT`、`PARTIALLY_SHIPPING`、`AWAITING_COLLECTION`、`IN_TRANSIT`、`DELIVERED`、`COMPLETED`、`CANCELLED`、`RETURN`

**子单（line）履约状态**（我们自己的状态机）
- `pending` 待发货 → `shipped` 已发出 → `failed` 失败（库存不足 / SKU 未映射 / 其他错误）

**卡密（code）状态**
- `free` 在库可用 → `locked` 被某子单锁定 → `used` 已发给买家 → 终态
- `void` 作废（不会再被取出，财务上不计入"已售成本"）
- `expired` 已过期

**采购单（PO）付款状态**
- `unpaid` → `partial` 部分付款 → `paid` 已结清

## 1. 看板（/dashboard）

进入后台默认页。**KPI 都是当日数字**（按 UTC 自然日切换）：

| 指标 | 含义 | 计算口径 |
|---|---|---|
| 今日 GMV | 今天产生的销售额 | `tts_orders.total_amount`（排除 CANCELLED / RETURN） |
| 今日订单数 | 同上 | 同上 |
| 待发货子单 | 当前堆积量 | `lines.status='pending'` |
| 在库可用卡密 | 全 SKU 总和 | `codes.status='free'` |
| 今日已发出 | 今天履约成功数 | `codes.status='used' AND used_at >= 今天0点` |
| 今日失败子单 | 需要人工干预 | `lines.status='failed'` |

下方有：
- **14 天 GMV 趋势 SVG 折线图**
- **低库存预警**（free < 20 张的 SKU 自动列出来）
- **最近失败订单**（点进去可以一键重发）

> ⚠️ 趋势图首次进站可能是平的——只要打过订单就会有数据。

## 2. 供应商档案（/suppliers）

### 2.1 字段说明
| 字段 | 必填 | 说明 |
|---|---|---|
| 名称 | ✓ | 全局唯一，不能重复 |
| 供应商类型 | ✓ | `手动采购` 或 `API 供应商` |
| 联系人 | | 一般是销售对接人 |
| 联系电话 | | 微信号也可以填这里 |
| 默认账期 | ✓ | 单位：天，建采购单时自动算应付日 |
| 备注 | | 自由文本 |
| API Host / App ID / Account ID / App Key | API 供应商必填 | 只有 `admin` 可以维护 |
| 默认币种 | API 供应商必填 | 必须和供应商钱包币种一致 |
| 启用 | | 关闭后不能再下新 PO |

### 2.2 操作

**新建手动供应商**
1. 点右上角「新建供应商」
2. 供应商类型选「手动采购」
3. 填名称（必填）、默认账期（默认 30 天）
4. 提交 → 列表刷新可见

**新建 API 供应商**
1. 点右上角「新建供应商」
2. 供应商类型选「API 供应商」
3. 填 API Host、App ID、Account ID、App Key、默认币种
4. 提交 → 列表刷新可见
5. 进入该供应商的「商品目录」确认能拉到商品

> 采购角色可以维护普通供货商资料；涉及 API 凭证时必须用 `admin` 账号。

**禁用供应商（"软删除"）**
- 点击该供应商行的「编辑」→ 取消勾选「启用」
- ⚠️ **如果该供应商还有未结清的 PO（`unpaid` 或 `partial`），系统会拒绝禁用**，提示先把账结清再说
- 这是故意的——避免账款关系丢失

**查看待结金额**
- 列表里 `未付清` 列就是该供应商当前总欠条数

> 没有"删除"按钮——供应商关系一旦建立就保留历史，避免老 PO 找不到归属。

## 3. TT 商品中心（/tts-products）

TT 商品中心用于从 TikTok Shop **只读同步已上架商品**，然后检查哪些 TT SKU 已经匹配到我们的内部库存 SKU。

重要边界：
- 后台**不会创建 TikTok 商品**，商品上架仍在 TikTok Shop 卖家中心完成。
- 后台**不会修改 TikTok 商品价格、标题、上下架状态**，当前只读同步。
- 同步后本地会保存 `product_id`、`sku_id`、`seller_sku`、售价、状态等快照，减少人工复制 ID。

### 3.1 页面指标

| 指标 | 含义 |
|---|---|
| TT SKU | 当前已同步到本地的 TT SKU 数量 |
| 已匹配 | 该 TT SKU 已经能命中 SKU 映射，来单后可按现有库存履约 |
| 未匹配 | 还没有对应的 SKU 映射，来单会 `sku_not_mapped` |
| 最后同步 | 最近一次从 TT Shop 拉商品的时间 |

### 3.2 同步 TT 商品

**入口**：`TT 商品` → 右上角「同步 TT 商品」

操作后系统会：
1. 拉取当前授权店铺的 TT 商品列表。
2. 拉取商品下的 SKU 信息。
3. 写入本地 `tts_products` / `tts_product_skus` 快照表。
4. 自动判断每个 TT SKU 是否已经命中现有 SKU 映射。

同步结果里出现错误时，先确认：
- 店铺刚加过 Product scope 后是否重新授权。
- 授权 scope 里是否有 `seller.product.basic`。
- 该商品是否属于当前授权店铺。

### 3.3 匹配状态怎么看

| 状态 | 含义 | 处理 |
|---|---|---|
| 已匹配 | TT SKU 已命中一个 active SKU 映射 | 一般不用处理，可以继续备货 |
| 未匹配 | 没找到对应 SKU 映射 | 点「去匹配」，系统会打开 SKU 新建弹窗并自动带入 TT 字段 |
| 冲突 | 同一个 TT SKU 命中多条 SKU 映射，或命中一条已停用映射 | 先暂停上新，进入 SKU 映射编辑现有记录；如果是停用映射，确认无误后重新启用 |

### 3.4 新品上架时怎么用

推荐流程：
```
TikTok Shop 卖家中心上架商品
  → /tts-products 同步 TT 商品
  → 找到未匹配的 TT SKU
  → 点「去匹配」，确认系统已带入 seller_sku / product_id / sku_id / 售价
  → 补内部 SKU、面额、安全库存并保存
  → 绑定供应商 / API 采购链接
  → 下采购单或 API 批量入库
  → 库存确认 free 数量
  → 来测试单后检查是否 shipped
```

如果 `TT 商品中心` 里没有同步到目标商品，先回 TikTok Shop 确认商品是否已审核通过、是否属于当前授权店铺；仍没有再找开发看 Product API 返回。

## 4. SKU 映射（/skus）

把"我们内部的 SKU"和"TT 上架的 SKU"绑定起来，履约程序按这个表把订单里的 `sku_id` 翻译成"该取哪种卡密"。

建议：新品优先从 `TT 商品中心` 同步后再建映射，少手填 `product_id` / `sku_id`。

### 4.1 字段说明
| 字段 | 必填 | 说明 |
|---|---|---|
| 内部 SKU | ✓ | 我们自己的命名，比如 `STEAM-USD-50` |
| 卖家 SKU | ✓ | 你在 TT 卖家中心填的 seller_sku |
| TT 商品 ID | | TT 商品维度 ID。一个商品可能有多个面值 SKU |
| TT SKU ID | | TT 平台返给我们的数字 ID（webhook 里会带） |
| 面值 | ✓ | 单位：美分。$50 卡填 `5000` |
| 售价 | | TT 售价，单位美分；用于价格倒挂/库存锁预警 |
| 安全库存 | | 单 SKU 阈值；为空时走全局阈值 |
| 锁库存 | | 风险、调价倒挂、人工停卖时才打开 |
| 启用 | | 关闭后履约不再使用此映射 |

匹配建议：
- 优先填 `seller_sku` + `TT 商品 ID` + `TT SKU ID`。
- 至少保证 `seller_sku` 能命中，否则订单会 `sku_not_mapped`。
- 多面值商品不要只靠 `product_id` 判断，必须确认到具体 `sku_id` / `seller_sku`。

### 4.2 操作

**从 TT 商品中心新建 SKU 映射（推荐）**
1. 进入 `TT 商品`。
2. 点击右上角「同步 TT 商品」。
3. 找到状态为「未匹配」的 TT SKU。
4. 点该行「去匹配」。
5. 系统跳到 `SKU 映射`。如果还没有映射，会自动打开「匹配 TT 商品」弹窗；如果已有映射，会筛出并自动打开现有记录。
6. 确认 `seller_sku`、`TT Product ID`、`TT SKU ID`、商品名、售价已经自动带入。
7. 补齐「内部 SKU」「礼品卡面额」「安全库存阈值」。
8. 点击「创建」。

如果页面提示“这个 TT 商品已经有 SKU 映射”，不要再新建。直接检查自动打开的编辑窗口：字段正确就保存；如果状态是 disabled，确认该商品要重新销售后勾选 `active` 再保存。

**手动新建 SKU 映射**
1. 进入 `SKU 映射`。
2. 点右上角「新增 SKU」。
3. 手动填写内部 SKU、面额、seller_sku、TT Product ID、TT SKU ID、售价。
4. 保存。

必须先建映射，**才能下采购单 + 导入卡密**，后端会校验 sku_id 在不在映射表里。

**配置 API 采购链接**
1. 在 `SKU 映射` 列表找到目标 SKU，点「编辑」。
2. 在「API 采购链接」区域点「添加链接」。
3. 选择 API 供应商。
4. 点「浏览商品」，从供应商商品目录选择对应礼品卡 SKU。
5. 确认外部 SKU ID 和外部面值。
6. 查看「供应商库存」：`不限` 代表供应商不限制库存；数字代表供应商实时可售数量；查询失败时先检查 API 凭证、外部 SKU 和供应商状态。
7. 点击「保存链接」。

> 「库存不足时自动采购」会影响真实订单发货，只允许 `admin` 打开。普通上货先只做链接和批量入库即可。

**禁用 SKU 映射（软删）**
- 点行尾「删除」实际只是 `active=false`
- 不会影响历史订单/库存数据

## 5. 采购单（/purchases）

供应商发货前/后录入，是**库存成本的源头**。

### 5.1 创建采购单

**入口**：列表右上角「新建采购单」

**填写要点**：
| 字段 | 说明 |
|---|---|
| PO 编号 | 留空时系统自动生成 `PO20260427-001` 风格；也可手填外部单号 |
| 供应商 | 下拉选已启用的供应商 |
| 内部 SKU | 必须是已建好的 SKU 映射 |
| 面值 | 美分 |
| 数量 | 卡密张数 |
| 单价 | 美分（你的进货成本） |
| 采购日期 | 默认今天 |
| 应付日 | 留空时按 `采购日 + 供应商默认账期` 自动算 |
| 备注 | 比如"含税"、"促销批次"等 |

**总价 `total_cost` = 数量 × 单价**，系统自动算，不用手填。

### 5.2 状态流转

```
unpaid (新建) ──┬──> partial（部分付款）──> paid（结清）
                └──> paid（一次付清）
```

**关键约束**
- ✅ 已 `paid` 的 PO **不能再修改**任何字段（防止财务漂移）
- ✅ 已 `paid` 的 PO **不能再付款**
- ✅ 已导入卡密的 PO（`batch_id != null`）**不能删除**
- ✅ 已有付款记录的 PO **不能删除**
- ✅ 同一张 PO **只能导入一次卡密**——再点导入会被拒绝

### 5.3 记录付款

1. 列表点 PO → 详情页 → 「记录付款」按钮
2. 填本次付款金额（美分） + 备注（可选）
3. 系统自动判断：
   - 累计 < 总价 → 状态变 `partial`
   - 累计 = 总价 → 状态变 `paid`，记录 `paid_at` 时间戳
   - 累计 > 总价 → 拒绝（金额超额）

### 5.4 修改采购单
- 已付清的不能改
- 修改 `数量` 或 `单价` 时，`total_cost` 自动重算
- 改完后**再付款时按新总价判断**

### 5.5 删除采购单
仅在以下条件**全部满足**时可删：
- 还没导入卡密
- 还没记录任何付款

否则需要先「冲销」——这个版本暂不支持冲销，请联系开发。

## 6. 库存（/inventory）

三个标签页：**汇总 / 批次 / 卡密明细**。

### 6.1 汇总 Tab
按 `(SKU, 面值)` 聚合，一眼看清每种卡现在有多少 free / locked / used / void / expired。

**用途**：日常看库存水位、决定要不要补货。

### 6.2 批次 Tab
每次「卡密导入」生成一个 batch_id，这里按批次列出来：
- 批次号（系统生成）
- 关联 PO 编号（点击可跳转）
- SKU、面值、数量、剩余 free / locked / used
- 最早导入时间

**用途**：追溯某批卡的来源、判断哪批快卖完、哪批是问题批次。

### 6.3 卡密明细 Tab
单张卡的最细颗粒度。可以按 `状态 / SKU / 批次` 过滤。

**用途**：
- 排查"这张码到底有没有发出去"
- 客服查询某子单对应的码
- 应急作废 / 解锁

> ⚠️ 这里**不显示明文卡密**——明文用 Fernet 加密存库，前端只看到状态/元数据。需要明文请走「客服取明文」流程（暂未实现）。

### 6.4 卡密导入

**入口**：库存页右上角「导入卡密」

**前置条件**：
- 必须先有一张**已下、未导入过**的采购单
- PO 状态对导入没要求（unpaid 也能导）

**操作步骤**：
1. 选采购单（下拉显示 `PO 编号 - SKU - 数量`）
2. 上传供应商文件，或在文本框粘贴明文卡密，**每行一张**
   ```
   AAAA-BBBB-CCCC-DDDD
   EEEE-FFFF-GGGG-HHHH
   ...
   ```
3. （可选）填过期时间
4. 确认解析出的卡密数量，再提交

支持文件：
- `.txt` / `.text`：每行一张卡密
- `.csv` / `.tsv`：优先读取列名包含 `code`、`card_code`、`pin`、`卡密`、`兑换码`、`密码` 的列
- `.xlsx`：按同样规则读取 Excel 工作表；如果是旧版 `.xls`，先另存为 `.xlsx` 或 CSV

如果供应商文件里“卡号”和“密码”分两列，系统会合并成一行保存，例如 `AAAA-BBBB | 1234`。

**系统会做**：
- 自动 SHA-256 哈希计算指纹（`code_hash`）
- 同指纹与历史库内已存在的码 → 跳过（不会重复入库）
- 用 Fernet 加密明文存库（`code_ciphertext`）
- 生成 batch_id，回写到 PO 上
- 写一条审计日志

**返回信息**：
```
导入成功！
total: 100   你提交了多少行
inserted: 98 实际入库
skipped_duplicate: 2  重复跳过
batch_id: bch_xxx
```

如果 `inserted=0`（全是重复），系统回滚整次操作，PO 不会被标记为已导入。

### 6.5 作废卡密 (Void)

**用途**：发现某张码已被供应商盗用 / 已在别处兑换过 / 物理卡损坏

**操作**：卡密明细页 → 找到该码 → 行尾「作废」按钮
- `free` / `locked` / `expired` 状态下都可作废
- ❌ `used` 状态（已发出去）不能作废——已经在客户手里了

作废后该码的 `unit_cost` **不计入"已售卡密成本"**，但仍计入"在库成本"快照（供以后做对账时识别损耗）。

### 6.6 解锁卡密 (Unlock)

**用途**：极少数情况下子单卡死在 `pending`，把锁住的码退回库存
- 比如：worker 进程崩溃、Redis 故障期间留下的"僵尸锁"
- 比如：手动测试后想恢复

**操作**：卡密明细页 → 状态过滤选 `locked` → 找到该码 → 「解锁」
- ❌ 仅 `locked` 状态可解锁，其他状态拒绝

> ⚠️ 解锁前先确认对应的子单**真的失败了**，否则可能导致一码两发。

## 7. 订单管理（/orders）

### 7.1 列表过滤
- **status**：精确匹配 TT 订单状态
- **shop_id**：多店铺时按店筛选
- **q**：按订单号前缀搜（前缀匹配最快）
- **only_failed**：勾选后只看"至少有一个失败子单"的订单——日常排错入口

每行显示订单号、店铺、状态、金额、子单总数 / 已发 / 待发 / 失败的色块。

### 7.2 订单详情
点订单号进入详情页：
- **订单元信息**：买家不可见字段我们这里都有
- **处理建议**：如果有 failed 子单，系统会给出下一步按钮
- **子单列表**：每行显示 SKU、数量、状态、关联的卡密 ID、失败原因、处理入口
- **fulfillment 日志**：履约 worker 每一步都留了日志（lock / send / fail with reason）

失败子单处理入口：

| 失败原因 | 页面按钮 | 你要做什么 |
|---|---|---|
| SKU 未映射 / `sku_not_mapped` | 去匹配 SKU | 系统带入订单里的 TT 字段，补内部 SKU 和面额，保存后回订单重发 |
| 库存不足 / `no_stock` | 手动补码 / 去补库存 | 急单直接粘贴 CDK 补发；常规缺货先建采购单并导入卡密，或走 API 批量入库，库存 free 增加后回订单重发 |
| API 实时采购失败 | 看供应商采购 | 查看供应商返回错误，确认 API 凭证、外部 SKU、币种、供应商库存 |
| 手动补码回传失败 / `manual_code_redeem_failed` | 看日志 | 看 fulfillment 日志里的 TT 错误，确认后重新补码或联系开发 |
| 其他失败 | 查看 SKU | 检查映射、库存锁、供货商链接，再决定是否重发 |

> 处理建议只是把你带到正确页面；真正修好原因后，仍需要回到订单详情点「重发」。

### 7.3 手动补码

**用途**：
- 子单因为 `no_stock` 失败，但采购或客服已经在线下拿到一张 CDK
- 急单需要直接发给客户，不想等完整采购单 + 入库流程

**操作**：
1. 订单详情页找到失败子单，点击「手动补码」或「补码」
2. 粘贴 CDK
3. 填备注（建议写客服工单号或供应商来源）
4. 点击「确认补发」

**系统会做**：
- 把 CDK 加密写入 `codes`
- 直接锁定到该子单
- 调 TikTok redeem callback 发码
- 成功后子单变 `shipped`，卡密变 `used`
- 写 fulfillment 日志和审计日志

注意：审计日志不会保存明文 CDK；如果 CDK 已经导入过，系统会拒绝，避免重复发码。

### 7.4 重发订单（Reship）

**用途**：
- 子单 `failed`（卡密不足导致没发出去），补完库存后想重新尝试
- 客户投诉"没收到码"，确认后想再发一次

**操作**：
1. 详情页右上角「重发」按钮
2. 弹窗里填备注（强烈建议写原因，进审计日志）
3. 确认

**系统会做**：
- 造一条虚拟 `webhook_event`（type=`ADMIN_RESHIP`），带上你的 username + 备注
- 推到 arq 队列，触发 `fulfill_order` worker
- worker 走和正常履约**完全相同**的逻辑：找映射 → 锁码 → 调 TT API 发货 → 更新状态
- 写审计日志（包含 event_id 和 job_id）

**幂等性**：
- 重发请求会用 `admin-reship:{order_id}:{随机12位}` 做去重 key
- 同一订单连点两次「重发」会触发**两次**履约（这里故意不去重——你点两次就是真要发两次）
- 但如果某子单已经 `shipped`，worker 不会重复发那个子单

> ⚠️ 重发后**结果不是立刻可见**的——worker 跑完一般 3-10 秒。刷新页面看 fulfillment 日志确认。

不要连续点击重发。原因没修好之前反复重发，只会重复产生失败日志。

### 7.5 关于"退货"

我们系统**不主动处理退款**——退款发生在 TT 平台侧，由 TT 把订单状态推到 `RETURN` 或 `CANCELLED`。我们这边的处理是：

| TT 推送的状态 | 我们的反应 | 你需要做什么 |
|---|---|---|
| `CANCELLED`（订单整单取消） | 自动忽略未发的子单；已 `locked` 的卡会被释放回 `free` | 一般无需操作 |
| `RETURN`（已发货后退货） | 状态记录下来；卡已经发到客户手里了 | 1. 确认是否要把已 `used` 的码标记 `void`（避免再发）<br>2. GMV 自动从有效销售里扣除 |
| 子单 `failed` 但客户没投诉 | worker 已经记日志 | 看清原因，缺货就补货后重发；SKU 没映射就建映射 |

财务影响：
- `CANCELLED` / `RETURN` 状态的订单**不计入 GMV**（财务和看板都自动排除）
- 已发出去的卡如果想"作废"，去库存→卡密明细→对那张 `used` 状态的码点不可——`used` 不允许 void。这种情况只能在**新订单**里用别的码补发。

## 8. 财务（/finance）

### 8.1 总览 KPI（默认 30 天窗口）

| 指标 | 计算 |
|---|---|
| GMV | 窗口内非取消/退货订单的 `total_amount` 之和 |
| 平台抽成（估算） | `GMV × 0.06`（可在 `.env` 改 `tt_platform_commission_rate`）|
| 已售卡密成本 | 窗口内 `codes.status='used'` 关联到 PO 的 `unit_cost` 之和 |
| 在库成本 | 当前 `free + locked` 状态的卡的 `unit_cost` 之和（**快照值**，不限窗口）|
| 毛利 | `GMV - 平台抽成 - 已售卡密成本` |
| 应付总额 | 所有未结清 PO 的 `(total_cost - amount_paid)` 之和 |
| 逾期应付 | 上面这部分里 `payment_due_date < 今天` 的金额 |
| 历史无成本码 | `status='used'` 但 `purchase_order_id IS NULL` 的卡数（迁移前的老数据） |

> ⚠️ 平台抽成是**估算值**——TT 真实抽成是按品类 + 阶梯算的，要精确数请等接 TT 结算单 API。当前后台按 6% 估算。

### 8.2 月度趋势图
最近 12 个月的 GMV vs 卡密成本 双柱图：
- GMV 按订单 `update_time_tt` 月聚合
- 成本按 PO `purchase_date` 月聚合
- 注意：**两条线的月份可能错位**——9 月进的货可能 10 月才卖出去

### 8.3 切换窗口
URL 里 `?range_days=7` / `?range_days=90` 可改窗口（前端选择器在路上）。

## 9. 用户管理（/users）

只有 `admin` 角色能看到并操作「用户管理」。

### 9.1 角色说明

| 角色 | 适合谁 | 当前权限 |
|---|---|---|
| `admin` | 负责人 / 系统管理员 | 可管理账号；其他业务页面可操作 |
| `ops` | 运营 | 可登录并处理日常业务 |
| `purchase` | 采购 | 可登录并处理采购库存相关业务 |
| `finance` | 财务 | 可登录并看财务、采购付款 |
| `support` | 客服 | 可登录并处理订单查询、客诉 |

当前版本已经按角色收敛菜单，并在后端 API 做权限校验：

- `admin`：全部权限，含用户管理、审计日志、API 凭证、自动采购开关。
- `ops`：看板、订单、库存、TT 商品、SKU 映射、供应商采购等日常运营；不能看财务和用户管理。
- `purchase`：库存、TT 商品、SKU、供货商、采购单、API 批量采购；不能管理用户和审计。
- `finance`：财务、采购单查看/付款、供货商只读。
- `support`：看板、订单查询/重发、库存/SKU/TT 商品只读、供应商采购只读。

> 「API 供货商凭证」和「库存不足时自动采购」属于高风险配置，只有 `admin` 可以修改。

### 9.2 创建账号

1. 进入 `用户管理`。
2. 点「新增用户」。
3. 填用户名、初始密码、角色、显示名、备注。
4. 保持「启用账号」勾选。
5. 提交后把用户名和初始密码发给对方，提醒首次登录后找管理员改密码。

### 9.3 停用 / 重置密码

- 离职或临时账号不用了：编辑用户 → 取消「启用账号」。
- 忘记密码：点该用户行的「重置」→ 输入新密码。
- 系统禁止停用自己，也禁止移除最后一个启用的管理员，避免后台锁死。

## 10. 审计日志（/audit）

**所有写操作都自动记录**，是排查"谁在什么时候做了什么"的唯一来源。

### 10.1 记录的动作

| action | 触发时机 |
|---|---|
| `login` / `logout` | 登录登出 |
| `login_failed` | 输错密码 |
| `login_locked` | 触发锁定 |
| `user_create` / `user_update` / `user_reset_password` | 用户管理 |
| `reship` | 手动重发订单 |
| `import` | 导入卡密 |
| `void` / `unlock` | 作废 / 解锁卡密 |
| `sku_create` / `sku_update` / `sku_delete` | SKU 映射 CRUD |
| `tts_product_sync` | 同步 TT 商品中心 |
| `supplier_create` / `supplier_update` | 供应商 CRUD |
| `purchase_create` / `purchase_update` / `purchase_pay` / `purchase_delete` | 采购单 CRUD + 付款 |

### 10.2 字段说明
| 字段 | 含义 |
|---|---|
| 操作者 | 登录用户名 |
| 动作 | 上表 action |
| 目标类型 | order / code / batch / sku / supplier / purchase / tts_products / admin_user |
| 目标 ID | 对应实体的主键 |
| 详情（JSON） | 操作前后值、备注、IP 等 — 折叠展开 |
| 时间 | UTC 时间 |

### 10.3 过滤
- 按操作者
- 按动作类型
- 按目标类型

### 10.4 写入策略
- 单一写入函数 `write_audit()` 集中实现
- 大多数操作把 audit 写在主事务里**一起 commit**——保证"操作做了，日志一定也写了"
- 例外：`login_failed` / `login_locked` 因为不在用户事务上下文，单独 commit

> 审计日志**只读不可改**——后端 API 没有提供修改/删除接口。

## 11. 内容创作（/content）

内容创作模块用于把外部视频或本地视频处理成可复用素材，再生成短视频脚本和成片。它不影响订单履约，但会占用服务器 CPU/磁盘，长视频处理会比较慢。

### 11.1 素材采集

入口：`/content/ingest`

支持两种方式：

| 方式 | 适合场景 | 注意事项 |
|---|---|---|
| 本地上传 | 已经下载好的 mp4 / mov / mkv / webm 等视频 | 最稳定，推荐作为默认流程。 |
| URL 抓取 | YouTube、TikTok、B 站、Steam 商品页等公开链接 | YouTube 生产环境建议配置 cookies；Steam 会尝试抓官方 trailer，没有 trailer 时需本地上传。 |

操作：

1. 选择对应游戏，方便后续按游戏筛选素材。
2. 本地上传时可一次选多个视频；URL 抓取时一行一个链接。
3. 如视频上下有水印或黑边，填写顶部/底部裁剪像素。
4. 提交后看「最近采集」里的状态、阶段和进度。
5. 完成后进入 `/content/library` 复核片段。

状态说明：

| 状态 | 含义 | 操作 |
|---|---|---|
| 排队中 | 已创建任务，等待后台处理 | 等待即可。 |
| 处理中 | 正在下载、清理画面、ASR、切镜头或打标 | 看进度条和阶段；长视频几分钟是正常的。 |
| 已完成 | 素材已经切片入库 | 去素材库复核。 |
| 失败 | 任务失败，页面会显示原因 | 修正链接/文件后点「重试」。 |

常见失败：

- `YouTube 要求登录或人机验证`：更新服务器上的 YouTube cookies，或先本地上传救急。
- `YouTube 没有返回当前可下载格式`：先点「重试」；如果仍失败，更新素材服务镜像后再试，急用时先本地上传。
- `Steam 页面没有可抓取视频`：该商品没有 trailer 或 Steam 未返回可下载视频源，换有预告片的商品页或本地上传。
- `页面没有可直接抓取的视频`：换具体视频链接，或把视频文件下载后上传。
- `素材文件不存在或已被清理`：重新上传。

### 11.2 任务监控

入口：`/content/jobs`

这里能看到所有内容创作后台任务。排查素材采集时重点看：

- `kind=素材处理`
- `stage=download / watermark / asr / scenes / tag`
- `error` 和日志最后几行

如果采集页显示失败，但错误不够清楚，先到任务监控展开对应任务。

### 11.3 素材库

入口：`/content/library`

素材库展示已经入库的切片。生成视频前建议先复核：

- 是否属于正确游戏。
- 是否含真人脸、真人手部或主播画面。
- 片段描述、标签是否明显异常。
- 画面是否有黑边、水印或无关内容。

## 12. 典型工作流（最常用的几条线）

### 12.1 上新品 SKU
```
TikTok Shop 卖家中心上架商品
  → /tts-products 同步 TT 商品
  → 确认目标 TT SKU 是未匹配/已匹配
  → 在 TT 商品中心点「去匹配」，系统会带入 seller_sku / product_id / sku_id / 售价
  → /skus 弹窗里补内部 SKU、面额、安全库存并保存
  → 新建供应商（如还没有）
  → 手动采购：/purchases 下第一张采购单 → 收到卡密 → /inventory 导入
  → API 采购：/skus 编辑 SKU → 绑定 API 采购链接 → /purchases API 批量入库
  → 看板的"在库可用"出现新数字
```

### 12.2 客户没收到卡，要求补发
```
客服核对订单号
  → /orders 列表搜订单号
  → 详情页看子单状态
    → 如果是 failed：先看「处理建议」卡片
      → 库存不足 → 急单点「手动补码」；常规缺货先补货（走 11.1 后半段），再点重发
      → SKU 没映射 → 点「去匹配 SKU」建映射，再点重发
      → 供应商采购失败 → 点「看供应商采购」查看 API 错误，再点重发
    → 如果是 shipped 但客户说没收到 → 联系 TT 客服核实，必要时走重发
  → 重发后 10 秒内刷新看 fulfillment 日志
  → /audit 留有完整记录
```

### 12.3 月度对账
```
/finance 总览 → 看 GMV / 毛利 / 应付
  → 应付逾期金额 > 0 → 进 /purchases 过滤 unpaid + partial 找出来
  → 把要付的款记到对应 PO 上（用真实付款金额，不要凑整）
  → /audit 过滤 action=purchase_pay 自查这个月所有付款记录
  → 月度图表导出（暂未实现，需要导出请用 PostgreSQL 客户端直连）
```

### 12.4 发现某批卡有问题（卖家说被盗用了）
```
/inventory 批次 Tab → 找到这批
  → 切到卡密明细 → 按 batch_id 过滤
  → 状态 = free / locked 的：批量作废（当前没批量按钮，需逐张点—或联系开发加）
  → 状态 = used 的：联系已下单客户主动补发新码，原码标记保留
  → /suppliers 找到供应商，备注栏记录该批问题
  → 必要时禁用供应商（先结清 PO）
```

## 14. 出问题怎么办

| 现象 | 先看 | 再看 |
|---|---|---|
| 登录失败 | 密码对不对 | `/audit` 看自己 IP 是不是被锁 |
| 页面报 401 | cookie 过期 | 重新登录 |
| 页面报 403 | 不应该出现 | 联系开发 |
| 页面卡转圈 | F12 网络 Tab 看具体哪个请求挂了 | 截图给开发 |
| 数据看着不对 | 跟 `/audit` 操作记录交叉对比 | 必要时直连 DB 查 |
| 重发后没动静 | 等 10 秒，看 `/orders` 详情页 fulfillment 日志 | `docker logs tts-worker` |
