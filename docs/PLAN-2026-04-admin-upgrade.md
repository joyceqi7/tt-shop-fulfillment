# Game Code Hub 后台升级计划（2026-04）

## 1. 背景与目标

本次升级目标是把后台从“履约管理系统”提升为“运营 + 财务 + 售后 + 客服协同系统”，覆盖以下业务反馈：

- 订单页改版：去店铺列，增加顾客信息与筛选
- 看板增加按供货商/开发商维度销售分析
- 新增待支付、待处理售后、服务工单指标
- 订单页增加 TT 结款状态
- 毛利口径调整为：售出价格 - 成本 - 平台抽成（6%）
- 客服接入
- 评估并接入达人推广、活动折扣、粉丝与转化数据相关能力

---

## 2. 范围拆分（按可落地程度）

### 2.1 P0：本期必须上线（不依赖 TT 新权限）

1) 订单页结构升级  
2) 看板运营指标增强（先做本地可计算部分）  
3) 财务毛利口径改为 6%  
4) 工单与售后 MVP（本地模型）

### 2.2 P1：依赖 TT Shop API（需申请/验证权限）

1) TT 结款状态  
2) 平台活动折扣归因  
3) 达人推广指标（达人数/成交额）  
4) 退款人数/退款金额自动同步

### 2.3 P2：中长期（跨系统数据源）

1) 粉丝数据  
2) 商品曝光、点击、转化漏斗（曝光->点击、点击->成交）  
3) 客服系统深度集成（多渠道会话）

## 3. 业务需求映射与实现策略

## 3.1 订单页面改造

### 需求
- 删去“店铺列”
- 增加可筛选顾客信息：邮箱、TT ID、产品名
- 增加 TT 结款状态列

### 方案
- 前端表格字段重排：订单号 / 顾客 / 产品 / 订单状态 / TT结款状态 / 金额 / 更新时间
- 后端 `admin/orders` 增加查询参数：
  - `buyer_email`
  - `buyer_tt_id`
  - `product_name`
  - `settlement_status`
- 数据层新增（或回填）结构化字段，避免仅依赖 `raw_payload`

### 备注
- 当前库里已存在 `buyer_email_encrypted` 字段，但尚未完成入库链路，需补齐采集和解密展示策略（仅后台可见、脱敏显示）。

---

## 3.2 看板升级

### 需求
- 分供货商/开发商货品售卖情况
- 用户待支付个数
- 待处理售后
- 服务工单

### 方案
- 新增 4 组看板模块：
  - 供货商销售排行（销量、销售额、毛利）
  - 开发商/发行商销售排行（依赖 SKU 维度扩展字段）
  - 待支付订单数（按可配置口径）
  - 待处理售后数 + 未关闭工单数

### 数据定义（先约定）
- 待支付：订单状态处于未完成付款状态的订单数（可按 TT 状态映射）
- 待处理售后：状态 in `pending/reviewing` 的售后单
- 服务工单：状态 in `open/in_progress` 的工单

---

## 3.3 毛利计算调整

### 需求
- 毛利 = 售出价格 - 成本 - 平台抽成 6%

### 方案
- 将配置 `tt_platform_commission_rate` 调整为 `0.06`
- 财务页、看板、文档统一改口径
- 保留配置化，便于后续按店铺或品类差异化

---

## 3.4 客服接入

### 目标
- 先解决“可追踪、可分配、可闭环”

### MVP 方案（本期）

  - 审计日志记录

### 二期方案
- 对接第三方客服系统（飞书/企微/Zendesk）或 TT 客服能力

## 6. 风险与应对

- 风险：TT 某些 API 仅限特定区域/白名单  
  - 应对：先做本地可计算模块，不阻塞上线

- 风险：顾客隐私字段展示合规  
  - 应对：邮箱脱敏显示；导出权限受控；审计全链路记录

- 风险：订单多条件筛选性能下降  
  - 应对：结构化字段 + 索引 + 分页上限 + 慢查询监控

- 风险：口径不统一导致业务误解  
  - 应对：每个指标页面显示“口径说明”

---

## 7. 验收标准（Definition of Done）

- 订单页支持按邮箱、TT ID、产品名筛选，响应时间 < 1s（常规数据量）
- 看板可查看供货商/开发商销售情况
- 财务毛利按 6% 抽成计算，前后端口径一致
- 售后与工单可形成闭环（创建->处理->关闭）
- 结款状态可同步并显示（P1 完成后）
- 新增操作均可在审计日志追溯
